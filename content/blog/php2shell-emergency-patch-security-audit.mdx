## What happened with PHP2Shell, in plain language

PHP2Shell is the nickname for two vulnerabilities, **CVE-2026-109618** and **CVE-2026-109619**. Each carries a CVSS v4.0 score of **9.2 out of 10**. According to [CISA's alert on the critical PHP vulnerabilities](https://www.cisa.gov/news-events/alerts/2026/10/21/critical-vulnerabilities-php-require-immediate-patching), they allow **unauthenticated remote code execution**. In other words, an attacker doesn't need a password or an account. A crafted web request can be enough to run commands on your server.

What makes this one different is *where* the bug lives. It isn't in a plugin or a theme. It's in PHP's core memory handling. [Datadog Security Labs' technical analysis](https://securitylabs.datadoghq.com/articles/php2shell-critical-vulnerabilities-in-php/) reproduced the attack and found that the malicious request is processed before any application code runs, so your login screen, security plugin or application-level authentication cannot block it.

Once inside, an attacker runs with the web server's privileges. That can mean stolen files and database contents, defaced pages, hidden backdoors or spam and malware pushed to your visitors. The [Wiz Research write-up on PHP2Shell](https://www.wiz.io/blog/php2shell-php-rce) adds that some of the issues can also leak process memory, which may contain passwords, session tokens and API keys.

A few more PHP2Shell facts worth knowing:

- **The range is huge.** Wiz reports that every PHP release from the last decade, back to PHP 5.4, is affected by at least one of the issues.
- **Attacks started early.** Datadog notes that AWS reported exploitation attempts as early as 17 October, four days before public disclosure, and the [Cyber Security Agency of Singapore](https://www.csa.gov.sg/alerts-and-advisories/alerts/al-2026-151/) reports widespread exploitation attempts and multiple public proof-of-concept exploits.
- **Europe went dark as a precaution.** As [The Next Web reported](https://thenextweb.com/news/europe-governments-websites-offline-php-security-flaws), government, hospital, university and port websites across Europe, including the Port of Rotterdam, were taken offline while teams patched. The UK's NCSC told owners to update or take systems offline.
- **AI played a part.** The [Google Cloud blog on responding to PHP2Shell](https://cloud.google.com/blog/products/identity-security/responding-to-core-php-vulnerabilities-cve-2026-109618-cve-2026-109619) says Gemini 4 Argon helped find the vulnerability, develop the exploit, detect attacks and validate the patch. That cuts both ways: the same kind of tooling makes it faster for attackers to weaponise flaws at scale.

## Who is affected?

Short answer: PHP2Shell can reach almost anyone running PHP that serves web requests. [BleepingComputer's coverage of the emergency patches](https://www.bleepingcomputer.com/news/security/php-ships-emergency-patches-for-critical-php2shell-flaws/) lists PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP and LiteSpeed. That covers the setups used by most shared hosts, managed WordPress hosts and VPS deployments.

You are in scope if you run:

- A **WordPress** blog, brochure site or membership site. WordPress is written in PHP.
- A **WooCommerce** store, where customer data and order history sit on the same server.
- A **Laravel**, Symfony or CodeIgniter application, or a custom PHP back end.
- A Joomla, Drupal or Magento site, a client portal, a booking system or an old PHP tool nobody has touched in years.
- An **agency** portfolio of client sites on one or more hosting accounts.

Small businesses in the US, Canada, the UK and Europe are the quiet majority here. They rarely have an in-house security team, and a compromised site can mean lost sales, a blacklisted domain and, under GDPR or similar laws, a duty to report a data breach.

## Is my site vulnerable to PHP2Shell? How to check your PHP version

Before you can fix anything, you need to know what you're running. Pick whichever method suits you:

1. **Hosting control panel.** In hPanel, cPanel, Plesk and most managed hosts, the PHP version is shown under a "PHP Configuration", "Select PHP Version" or "MultiPHP Manager" section.
2. **WordPress dashboard.** Go to **Tools → Site Health → Info → Server**. The PHP version is listed there.
3. **Command line.** On a VPS, run `php -v`. Remember that the PHP-FPM version serving your site can differ from the CLI version, so check your web server's PHP pool too.
4. **Ask your host.** Managed and shared hosts often patch the PHP builds on their servers themselves, so ask whether their PHP packages already include the PHP2Shell fixes.

## How to fix PHP2Shell: your patch checklist

### 1. Update PHP to a patched version

The fixed releases are **PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35**, as listed in the [official PHP 8 ChangeLog](https://www.php.net/ChangeLog-8.php) and the [Vercel PHP2Shell security bulletin](https://vercel.com/kb/bulletin/php2shell-security-bulletin). If you're on one of those branches, update to the patched release and **restart PHP-FPM or your web server** so the old worker processes stop running vulnerable code.

### 2. Move off end-of-life PHP (8.1 and older)

PHP 8.1 and older no longer receive regular updates from the PHP project. The PHP security team published minimal source backports for 7.4, 8.0 and 8.1, and some Linux distributions and LTS vendors ship their own fixes. For most website owners on shared or managed hosting, the realistic route is to **update PHP version** to 8.2 or newer. Test before you switch, though. Older themes and plugins can break on newer PHP, so test on a staging copy, or at least take a full backup first.

### 3. Confirm your host's patch status

If you're on shared or managed hosting (Hostinger, SiteGround, Bluehost, cPanel or Plesk hosts), check your provider's status page or support channel and ask them to confirm their PHP build includes the fixes for CVE-2026-109618 and CVE-2026-109619. Choosing "8.3" in a panel only helps if the host has installed 8.3.36 behind it.

### 4. If you can't patch yet, take the site offline

This is exactly what CISA and the UK NCSC advise for systems that can't be updated right away. A few hours of maintenance mode is far cheaper than a breach. A web application firewall, such as Cloudflare's emergency rules, can buy time, but it is a stopgap, not a fix.

### 5. Check whether you've already been hit

Patching PHP2Shell closes the door. It doesn't remove anyone who walked in before you closed it. After you update, look for:

- **New or modified PHP files** you didn't create, especially in `wp-content/uploads`, theme folders and the web root.
- **Unknown administrator accounts** in WordPress or your application.
- **Odd log entries**: unusual POST requests, PHP workers starting shell commands or downloading tools, and traffic spikes on non-standard ports.
- **Unexpected cron jobs**, redirects, injected scripts or new outbound connections.

If you find anything, rotate passwords, API keys and database credentials, because PHP2Shell's memory-disclosure side means secrets may have leaked.

## Frequently asked questions

### Is my WordPress site affected by PHP2Shell?

Very likely, unless your host has already patched it. WordPress runs on PHP, and PHP2Shell sits in the PHP engine, not in WordPress itself. Updating WordPress core or your plugins does not fix it. The PHP version on your server has to be updated.

### How do I fix PHP2Shell?

Update the PHP runtime serving your site to a patched release, restart PHP-FPM or your web server, then check for signs of compromise. Updating WordPress or plugins alone does not fix it. If you'd rather not do it yourself, my [PHP2Shell patch service](/services/php2shell-emergency-patch) covers it end to end.

### Which PHP versions fix PHP2Shell?

PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35. PHP 8.1 and older are end-of-life. Use a vendor backport if you have one, or upgrade to a supported branch.

### Will updating my PHP version break my website?

It can, mainly on older themes and plugins when you jump across major branches. Staying on the same branch, for example 8.3.x to 8.3.36, is usually low-risk. That's why compatibility testing is part of my service.

### I'm on Hostinger or shared hosting. Am I patched?

Only if your host has installed the patched PHP build behind the version you select. In hPanel or cPanel, pick a supported branch (8.2 or newer), then confirm with support that the build includes the CVE-2026-109618 and CVE-2026-109619 fixes, and recheck Site Health.

### Does a security plugin or firewall protect me?

Not fully. The attack happens before WordPress or your application code runs, so application-level plugins can't stop it. A WAF can block known exploit patterns for a while, but patching is the only permanent fix.

### I've patched. Do I still need a WordPress security audit?

Yes, if your site was exposed before you patched. Exploitation attempts were reported before disclosure, and a patch doesn't remove backdoors or rogue admin accounts. A **WordPress security audit** confirms you're clean.
